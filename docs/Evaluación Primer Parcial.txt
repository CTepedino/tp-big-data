Evaluación
La entrega es correcta, ordenada y cumple con los elementos principales solicitados para el primer parcial. El grupo entiende que el proyecto Cloud Provider Analytics requiere una arquitectura basada en Data Lake por capas, con procesamiento batch para maestros/facturación y procesamiento streaming para eventos de uso. También identifica correctamente a Cassandra/AstraDB como la capa de serving para consultas analíticas.

La elección de Lambda Architecture es adecuada. La justificación es clara: existen datos batch como customers_orgs, users, resources, billing y encuestas, junto con eventos de uso en streaming. Se explica que Lambda permite resolver ambos escenarios sin forzar los datos batch a comportarse como streams, lo cual está bien alineado con la consigna.

El diagrama de arquitectura existe y representa la idea general de la solución, pero el documento no profundiza demasiado en los detalles visuales ni técnicos del diagrama. Se identifican las capas Landing, Bronze, Silver, Gold, Serving y Consumo, pero se podría haber hecho más explícito el flujo entre batch y streaming, el rol de quarantine, checkpointing, idempotencia y la carga hacia Cassandra.

El mapeo de requisitos a componentes es bueno. Relaciona ingesta batch con PySpark, ingesta streaming con Structured Streaming, Landing como zona inmutable, Bronze para tipificación y deduplicación, Silver para limpieza y joins, Gold para marts de negocio, Cassandra/AstraDB para serving y herramientas BI para visualización. También incluye una tabla de las 5V del Big Data, correctamente conectadas con Volumen, Velocidad, Variedad, Veracidad y Valor.

La principal debilidad está en el flujo de datos, que aparece demasiado resumido. Se menciona el pipeline, pero no hay una explicación suficientemente profunda sobre cómo se manejaría el paso de Landing a Bronze, de Bronze a Silver, de Silver a Gold y de Gold a Cassandra. Tampoco se profundiza en late data, withWatermark, schema evolution v1/v2, reglas de calidad específicas, quarantine o diseño query-first de las tablas Cassandra.

Las asunciones y riesgos son correctos pero muy sintéticos. Se mencionan volumen menor a 1TB/día, micro-batching, Colab, claves consistentes, latencia, duplicación, evolución de esquema, datos inválidos, performance, Cassandra e idempotencia. Sin embargo, están presentados como una lista general y no como una matriz desarrollada de riesgo, impacto y mitigación.

La estimación de esfuerzo y recursos es razonable: 2 a 3 semanas, 40 a 60 horas totales, con roles de Data Engineer, Data Engineer orientado a Cassandra y Data Analyst. Es aceptable para el alcance preliminar, aunque no detalla fases, entregables ni distribución de tareas con suficiente precisión.

Veredicto
Entrega buena y aprobada con margen. Cumple los puntos centrales, pero queda por debajo de las mejores porque es bastante sintética. Para mejorar, debería profundizar el flujo de datos, los riesgos, las reglas de calidad, el manejo de schema evolution y el modelado de Cassandra
